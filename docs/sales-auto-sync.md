# 매출 자동 동기화 — 켜는 법

우리 사이트 두 곳의 매출을 ERP 가 직접 끌어옵니다. 사람이 엑셀을 내려받아
올리는 단계가 사라집니다.

| 피드 | 사이트 | ERP 에서 어디로 |
| --- | --- | --- |
| `acscent-online` | acscent.co.kr | 매출 판매 줄 (온라인 매장) |
| `smoat` | smoat.co.kr | SMOAT 결제·월별 AI 원가 |

---

## 0. 한눈에

```
사이트                        ERP
──────                       ────
결제 확정
  └─ 빈 신호 POST ─────────▶ /api/neander/sync/signal
                               └─ 피드를 GET 해서 직접 읽는다
GET /api/erp/feed  ◀────────────┘
  (읽기 전용 · Bearer 토큰)

                             Vercel Cron 매일 03:00 KST
                               └─ 같은 라우트를 GET (신호를 놓쳤을 때의 그물)
```

**신호에는 금액이 없습니다.** 사이트는 "새 것이 있다"고만 말하고 ERP 가
피드에서 직접 읽습니다. 그래서 신호 토큰이 새도 남이 우리 매출을 조작할 수
없고, 신호를 놓쳐도 다음 주기 실행이 같은 것을 가져갑니다.

---

## 1. 토큰 만들기

세 개가 필요합니다. 각각 **다른 값**이어야 합니다 — 하나가 새면 하나만 잠글 수
있어야 하니까요.

```bash
# 세 번 돌려 서로 다른 값을 만드세요
openssl rand -base64 32
```

| 토큰 | 쓰는 곳 | 성격 |
| --- | --- | --- |
| A. acscent 피드 토큰 | acscent 가 검사, ERP 가 제시 | 온라인 주문을 읽는 열쇠 |
| B. smoat 피드 토큰 | smoat 가 검사, ERP 가 제시 | SMOAT 결제를 읽는 열쇠 |
| C. 신호 토큰 | ERP 가 검사, 두 사이트가 제시 | "가져가라" 한 마디만 |

A·B 는 관리자 로그인과 같은 무게입니다. C 는 새도 잃을 것이 거의 없습니다.

## 2. 환경변수

### acscent (Vercel 프로젝트 `acscent-identity`)

```
ERP_FEED_TOKEN       = <A>
ERP_SYNC_SIGNAL_URL  = https://<ERP 도메인>/api/neander/sync/signal
ERP_SIGNAL_TOKEN     = <C>
```

`ERP_FEED_TOKEN` 이 없으면 피드는 **열리지 않습니다** (503). `ERP_SYNC_SIGNAL_URL`
이 없으면 신호를 보내지 않습니다 — 로컬·미리보기 배포가 실수로 본사 ERP 를
두드리지 않게 하려는 것입니다.

### smoat (Vercel 프로젝트 `nara`)

```
ERP_FEED_TOKEN       = <B>
ERP_SYNC_SIGNAL_URL  = https://<ERP 도메인>/api/neander/sync/signal
ERP_SIGNAL_TOKEN     = <C>
```

### ERP (Vercel 프로젝트 `APP_TARGET=neander`)

```
ACSCENT_FEED_URL     = https://www.acscent.co.kr/api/erp/feed
ACSCENT_FEED_TOKEN   = <A>
SMOAT_FEED_URL       = https://www.smoat.co.kr/api/erp/feed
SMOAT_FEED_TOKEN     = <B>
NEANDER_SYNC_SIGNAL_TOKEN = <C>
CRON_SECRET          = <Vercel 이 Cron 요청에 붙이는 값>
```

`CRON_SECRET` 은 Vercel 프로젝트 설정에서 만들면 Cron 요청의 `Authorization`
헤더에 자동으로 붙습니다. 값이 없으면 주기 실행 라우트는 503 으로 닫힙니다.

**주기 실행은 하루 한 번입니다** (`vercel.json`, UTC 18:00 = KST 03:00). 실시간은
사이트 신호가 맡고, 주기 실행은 신호를 놓쳤을 때의 그물입니다. 한 시간마다
돌리려면 `schedule` 을 `"0 * * * *"` 로 바꾸세요 — **Vercel Pro 이상**에서만
배포됩니다 (Hobby 는 하루 한 번까지만 허용해 배포가 실패합니다).

`vercel.json` 은 같은 저장소를 쓰는 매장(ACSCENT) 프로젝트에도 걸립니다. 그쪽
빌드에는 이 라우트가 없어 하루 한 번 404 가 나지만 해는 없습니다.

## 3. 켜는 순서

1. **두 사이트를 먼저 배포합니다.** 피드가 없으면 ERP 가 끌어올 곳이 없습니다.
2. **자사몰 상품 키를 마스터에 더합니다.**
   ```bash
   npm run sync:site-keys            # 무엇이 바뀔지 보기
   npm run sync:site-keys -- --apply # 쓰기
   ```
   자사몰 상품 키(`image_analysis/50ml` 꼴)가 상품 별칭으로 들어가야 주문이
   상품으로 확정됩니다. 이걸 건너뛰면 **모든 주문이 조용히 검토 대기함으로
   갑니다** — 동기화는 성공했다고 말하면서요.

   ⚠️ 「마스터 적재」 버튼으로 하지 마세요. 그 버튼은 코드의 값으로 상품 문서를
   덮어써서, 상품 관리 화면에서 고친 판매가·재료비·별칭이 되돌아갑니다. 이
   스크립트는 빠진 키만 더합니다.
3. **매출 › 자동 동기화**에서 「지금 동기화」를 누릅니다.
4. 결과를 확인합니다. 새 줄 수, 검토 대기 건수, 사람이 봐야 할 것.

---

## 4. 시작일 — 왜 2026-09-01 인가

온라인 매출은 **2026-02~08 이 이미 엑셀로 적재**돼 있습니다 (관리자 주문 화면의
「페이히어 온라인」 시트). 그 구간까지 자동으로 받으면 같은 판매가 두 번
잡힙니다 — 엑셀 줄은 문서 번호가 달라 멱등키로 막히지 않기 때문입니다.

그래서 기본 시작일이 `2026-09-01` 입니다. **8월까지는 엑셀이 정본, 9월부터는
피드가 정본.**

과거 달을 자동으로 다시 받고 싶으면:

1. 매출 › 적재 › 적재 이력에서 그 달의 온라인 배치를 **되돌립니다**.
2. 자동 동기화 › 시작일을 그 달 1일로 옮깁니다.
3. 「과거 달 다시 받기」로 그 달을 받습니다.

순서를 지키지 않으면 그 달 온라인 매출이 두 배가 됩니다.

## 5. 규칙 요약

### 온라인 주문 → 판매 줄

- 품목 한 줄 = 판매 줄 한 개. 문서 번호는 `online_주문id_품목id` 로 **정해져**
  있습니다 (멱등).
- 상품은 **정가로** 찾고 금액은 **실제 받은 값**을 적습니다. 쿠폰 할인은 주문
  단위라 품목 소계 비율로 나누고, 할인 근거(정가·할인율)를 줄에 남깁니다.
- 배송비는 첫 줄의 금액에 더하고 `shippingFee` 에 얼마인지 남깁니다.
- 전액 환불·취소·인플루언서 증정은 줄을 **지웁니다** (휴지통에 원본이 남습니다).
- **부분 환불은 사람에게 묻습니다.** 어느 품목을 돌려줬는지는 금액만으로 알 수
  없어서, 검토 대기함으로 보냅니다.
  - ⚠️ acscent 의 환불 라우트는 금액이 일부여도 주문 상태를 `cancelled` 로 바꿉니다.
    상태만 보면 부분 환불 주문이 **통째로** 매출에서 사라지므로, 피드는 상태가
    아니라 **금액**으로 판정합니다 (돌려준 돈 < 결제액이면 매출).
  - 같은 이유로 acscent 관리자 **원가계산 화면은 부분 환불 주문을 통째로 빼고
    있습니다.** 두 숫자가 다르면 ERP 쪽이 맞습니다.
- 쿠폰 반올림으로 사이트가 1원 더 받거나 덜 받은 주문은 그 1원을 첫 줄에 얹어
  적재합니다. 2원 이상 어긋나면 적재하지 않습니다.
- 사이트가 준 금액끼리 맞지 않으면 그 주문은 **적재하지 않고** 알립니다.

### 사람이 이깁니다

검토 대기함에서 사람이 **고친** 줄과 **지운** 줄은 동기화가 건드리지 않습니다.
지운 줄을 되살리지도 않습니다. 사이트 금액과 달라지면 「사람이 봐야 할 것」에
남습니다. 사람이 판단해 확정한 것을 기계가 조용히 되돌리면 그 사람은 다시는 이
화면을 믿지 않습니다.

### 잃지 않습니다

적재하지 못한 주문(금액이 안 맞거나 품목·날짜가 없는 주문)은 **풀릴 때까지**
「사람이 봐야 할 것」에 남습니다. 실행 결과에만 적으면 다음 실행이 덮어써
사라지고, 커서는 이미 지나갔으니 그 주문은 다시 오지 않기 때문입니다. 사이트에서
고쳐져 다시 들어오면 저절로 내려가고, 사람이 「확인」을 눌러도 내려갑니다.

### 한 번에 하나, 그래도 놓치지 않게

신호와 주기 실행이 겹치면, 늦게 읽은 실행이 먼저 읽은 옛 값으로 줄을 되살릴 수
있습니다(결제됨을 읽은 실행이, 취소를 읽고 지운 실행 뒤에 씀). 그래서 사이트마다
임대를 잡고 한 번에 하나만 돕니다.

잡혀 있을 때 온 신호는 버리지 않고 「한 번 더」 표시를 남깁니다. 도는 실행이 이미
피드를 읽은 뒤라면 그 사이 결제를 못 봤기 때문입니다. 도는 실행이 끝나면 표시를
보고 이어서 한 번 더 돕니다 (한 번 부름에 최대 세 차례). 주기 실행이 하루 한
번이라, 이게 없으면 겹친 결제가 최대 하루 늦게 들어옵니다.

### 커서는 늘 앞으로 갑니다

커서는 (수정 시각, id) 짝입니다. 같은 ms 에 바뀐 주문이 한 쪽(300건)보다 많아도
id 로 순서가 정해져 멈추지 않습니다. 커서 열쇠는 사이트가 만들고 사이트가 읽는
문자열이라 ERP 는 저장했다가 돌려줄 뿐입니다.

### 사이트에서 지운 주문

관리자 화면에서 주문을 지우면 그 주문은 피드에 다시 나타나지 않습니다. 바뀐 게
아니라 없어졌으니까요. 그래서 ERP 가 가진 주문 id 를 모아 사이트에 「아직 있나」를
되묻고, 돌아오지 않은 주문의 줄을 치웁니다 (휴지통에서 되돌릴 수 있습니다). 이
확인은 무거워서 하루 한 번의 주기 실행, 사람이 누른 「지금 동기화」, 사이트의
주문 삭제 신호에서만 돕니다.

### SMOAT

- `크레딧 충전 · 무통장 수기 지급 · 정기구독` 세 갈래를 받습니다. 지금 실매출은
  크레딧 충전이 거의 전부입니다 — 정기구독은 다날 정기결제 심사가 끝나지 않아
  사이트에서 꺼져 있습니다.
- 매출은 **환불을 뺀 순매출**입니다. 사이트의 `/admin/costs` 는 환불을 상태로만
  걸러서 부분취소가 남아 있습니다. 두 숫자가 다르면 ERP 쪽이 맞습니다.
- 월별 AI 원가와 크레딧(판 것·쓰인 것)을 함께 받습니다. 판 것에서 쓰인 것을 뺀
  누계는 **선수금의 근사치**입니다 — 쓰인 크레딧에 무료 체험·프로모션 크레딧의
  사용분이 섞여 있어 실제보다 작게 나옵니다.
- 무통장 수기 지급은 매번 **통째로** 받아 맞춥니다. 수기 지급이 나중에 충전에
  연결되면 같은 돈이 두 줄로 잡힐 수 있어서, 사라진 수기 지급 줄은 지웁니다.

## 6. 사이트 쪽에서 바뀐 것

두 사이트에 피드·신호를 붙이면서 **기존 동작도 몇 가지 고쳤습니다.** 배포할 때
함께 나갑니다.

**acscent**

- 무통장 입금 확인(`pending → paid`, 관리자 주문 화면)에서 `paid_at` 을 채웁니다.
  전에는 비어 있어서 매출일이 입금일이 아니라 주문일로 잡혔습니다 — 8/31 에
  주문하고 9/1 에 입금한 건이 8월로 갔습니다.
- 신호를 보내는 자리: 결제 검증 · 결제 웹훅(확정·취소) · 관리자 환불 · 무통장 환불 ·
  주문 상태 변경 · 인플루언서 설정 변경 · 주문 삭제.

**smoat**

- 신호를 보내는 자리: 크레딧 충전 확정 · 충전 환불 · 무통장 수기 지급.
- 기존 동작은 바꾸지 않았습니다.

## 7. 개인정보

피드에는 개인정보가 없습니다.

- 온라인: 수령인·전화·주소·메모를 `select` 하지 않습니다. 주문번호까지만.
- SMOAT: 원장(Staff)의 이름·이메일·전화를 보내지 않습니다. 학원 이름까지만.

학원 이름과 주문번호는 장부의 입금자명과 맞춰 보고 CS 로 되짚기 위해 필요합니다.

## 8. 확인


합계가 맞는지, 멱등한지, 할인·배송비·환불이 뜻대로 붙는지, 자사몰 상품 키가
전부 마스터에 걸리는지를 검사합니다.

## 9. 무엇이 잘못될 수 있나

| 증상 | 원인 | 할 일 |
| --- | --- | --- |
| 동기화 화면이 붉다 (하루 넘게 실패) | 토큰·주소가 틀렸거나 사이트가 내려감 | 결과 줄의 오류 메시지를 봅니다 |
| 「피드 계약 판이 다릅니다」 | 한쪽만 배포됨 | 양쪽 `contract` 를 맞추고 함께 배포합니다 |
| 전부 검토 대기함으로 감 | 마스터에 상품 키가 없음 | `npm run sync:site-keys -- --apply` |
| 그 달 매출이 두 배 | 엑셀 적재를 안 되돌리고 과거 달을 받음 | 엑셀 배치를 되돌립니다 |
| 신호가 안 옴 | 사이트에 `ERP_SYNC_SIGNAL_URL` 없음 | 주기 실행이 메우므로 급하지 않습니다 |
| 「피드의 커서가 앞으로 가지 않습니다」 | 사이트 피드 라우트가 옛 판이거나 고장 | 사이트의 `src/app/api/erp/feed` 를 확인합니다 |
| 「이미 동기화가 돌고 있습니다. 끝나면 이어서 반영됩니다」 | 신호와 주기 실행이 겹침 | 정상입니다. 도는 실행이 끝나면 한 번 더 돕니다 |
